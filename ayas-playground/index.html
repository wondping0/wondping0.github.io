THE TRUST BOUNDARY / 03

A receipt.
Not a leap of faith.

Showing the handout can spoil the puzzle. Verification checks the author's solver before the listing can be published. Re-flaggable bundles use a throwaway flag; static bundles use their fixed flag.

Solvable in the checked run.

The solver must recover the test flag without receiving it as input. A passing verdict is tied to the version that was tested.

Fresh flags, honest limits.

Re-flaggable bundles receive an order-specific flag; generate mode reruns the generator. Static bundles retain the same fixed flag for every buyer. Per-order flags support traceability, not copy protection.

Verification does not prove there are no unintended solutions, or that every event configuration will work unchanged.

BEFORE YOU BEGIN / 05

A few things
to know.

Can I purchase a challenge here?+

This is the public project introduction. The marketplace is in development; this page has no checkout, login, live listings, or payment collection.

Does it host my CTF?+

No. Buyers receive an artifact to deploy on their own infrastructure. Event hosting, live instances, and scoreboards belong to your CTF platform.

Can it run without Docker?+

The application can boot with an in-memory store and a stub runner for UI development. The stub can never pass verification. Real verification and fulfillment require the Docker runner.

What is included in v1?+

Cryptography challenges, version-bound verification, order-specific flags, and licensed delivery. Payouts are released manually. Other challenge categories and hosted events are outside v1.
